# 좌석 임시 점유 Frontend 연동

## 1. 문제와 목표

기존 좌석 선택은 브라우저 메모리의 `selectedSeats`만 변경했다. 두 사용자가 같은 좌석을 선택해도 결제 직전까지 서로의 선택을 알 수 없고, Frontend가 표시하는 선택 상태에는 서버가 보장한 소유권이 없었다.

이번 변경은 Backend가 이미 제공하는 임시 점유 계약을 예매 화면에 연결한다. 사용자가 좌석을 선택했을 때 서버가 성공 응답으로 돌려준 좌석만 "내가 선택한 좌석"으로 취급하고, 해제·만료·경합 응답을 화면 상태에 반영한다. 실제 PG나 운영 API를 호출하지 않고 명시적인 fixture로 계약을 검증한다.

## 2. Backend 계약

| 동작 | 요청                                         | 성공 결과                        | 주요 실패                                                   |
| ---- | -------------------------------------------- | -------------------------------- | ----------------------------------------------------------- |
| 점유 | `POST /main/detail/{concertId}/seat-holds`   | 좌석별 `seatNumber`, `expiresAt` | 400 잘못된 요청, 401 미인증, 409 다른 사용자 점유·예약 완료 |
| 해제 | `DELETE /main/detail/{concertId}/seat-holds` | 204 No Content                   | 인증·소유권·요청 검증 실패                                  |

요청 본문은 `concertTimeId`와 `seatNumberList`를 사용하고 쿠키 인증을 위해 `withCredentials`를 지정한다. 개발 환경에서는 Axios 기본 경로 `/api`를 Vite가 `http://localhost:18080`으로 전달한다. 배포 환경이 다시 생기면 `VITE_REACT_APP_AXIOS_BASE_URL`로 명시할 수 있다.

Backend에서 같은 사용자의 재요청은 기존 점유 만료 시각을 연장하지 않는다. 따라서 여러 좌석의 `expiresAt`이 같다고 가정할 수 없다.

## 3. 선택 상태의 원본

화면은 두 상태를 구분한다.

- 좌석 조회 결과: `AVAILABLE`, `HELD`, `RESERVED`와 같이 서버 전체 상태를 표현한다.
- `ownedHolds`: 현재 브라우저가 성공한 점유 응답으로 확보한 `좌석 번호 → 만료 시각`을 표현한다.

조회 응답의 `HELD`에는 소유자 정보가 없으므로 새로고침 뒤 그 좌석이 내 점유인지 판별할 수 없다. 이를 추측하지 않고 다른 사용자가 선택 중인 좌석으로 표시한다. 소유권 복구는 Backend 계약 확장 후 별도 Issue에서 다룬다.

## 4. 선택과 해제 흐름

### 선택

1. 사용자가 `AVAILABLE` 좌석을 누른다.
2. 현재 소유 좌석과 새 좌석을 합친 전체 목록을 정렬해 한 번의 POST로 보낸다.
3. 응답 좌석 집합이 요청 집합과 정확히 같고 모든 만료 시각이 유효할 때만 `ownedHolds`를 교체한다.
4. 좌석 목록을 다시 조회해 다른 좌석 상태도 최신화한다.

전체 목표 목록을 보내는 이유는 복수 좌석 점유의 성공 단위를 Backend 트랜잭션과 맞추기 위해서다. 일부 좌석만 응답하거나 만료 시각이 잘못된 응답은 부분 선택으로 수용하지 않는다.

### 해제와 화면 전환

- 선택한 좌석을 다시 누르면 해당 좌석을 DELETE하고 소유 목록에서 제거한다.
- 날짜·회차 변경과 상세 화면으로 돌아갈 때는 현재 소유 좌석 전체의 해제를 시도한다.
- 결제 화면으로 이동할 때는 결제 완료 전 소유권이 필요하므로 해제하지 않는다.
- 요청 중에는 좌석 전체 상호작용과 앱의 뒤로가기를 잠가 중복 클릭, 교차 요청, 응답 전 이동으로 인한 점유 누수를 막는다.

브라우저 종료·새로고침 시 비동기 DELETE의 전달 성공은 보장할 수 없다. cleanup에서 최선의 해제를 시도하지만, 최종 회수 책임은 Backend TTL에 있다. `sendBeacon`이나 별도 세션 복구 계약 없이 종료 시 즉시 해제를 보장한다고 기록하지 않는다.

## 5. 만료와 countdown

결제 가능 countdown은 소유한 모든 좌석 중 가장 빠른 만료 시각을 기준으로 계산한다. 한 좌석이라도 먼저 만료되면 기존 복수 좌석 묶음으로 결제를 계속할 수 없기 때문이다.

매초 활성 점유를 계산하고 만료된 좌석을 소유 목록에서 제거한 뒤 서버 좌석을 다시 조회한다. 다른 사용자의 정확한 만료 시각은 좌석 UI에 노출하지 않는다. 서버가 시간대 없는 `LocalDateTime` 문자열을 반환한다면 브라우저와 서버 시간대가 같다는 전제가 남으므로, 명시적 offset 계약은 후속 개선 후보다.

## 6. 오류 복구 정책

| 응답          | 사용자 동작                       | 화면 처리                           |
| ------------- | --------------------------------- | ----------------------------------- |
| 400           | 좌석·회차 요청 재확인             | 선택을 만들지 않고 최신 좌석 재조회 |
| 401           | 로그인 필요                       | 안내 후 로그인 화면 이동            |
| 409           | 다른 사용자가 먼저 점유 또는 예약 | 선택을 만들지 않고 최신 좌석 재조회 |
| 기타·네트워크 | 재시도 가능                       | 일반 실패 안내, 최신 좌석 재조회    |

실패 응답에서는 요청 전 소유 상태를 임의로 성공 처리하지 않는다. 해제 실패 시 화면 전환을 영구 차단하지 않으며, 남은 서버 점유는 만료 시각에 회수된다는 한계를 안내한다.

## 7. Fixture 검증 범위

- API 계층의 POST·DELETE 경로, body, 쿠키 옵션
- 점유 응답 전체성 검증과 좌석별 만료 시각 정규화
- 복수 좌석 선택 시 현재 소유 좌석을 포함한 전체 목록 POST
- 단일 좌석 해제와 회차 전환 시 DELETE
- 점유 응답 전 앱 뒤로가기 차단과 응답 후 전체 DELETE
- 400·401·409에서 부분 선택을 만들지 않는 복구
- 가장 빠른 만료 시각 countdown과 만료 후 소유 상태 제거
- 결제 화면 이동 시 cleanup DELETE를 생략하고 예약 데이터 전달
- 다른 사용자 `HELD`와 내 점유의 시각적·접근성 구분

이 결과는 로컬 fixture에서 Frontend 상태 전이가 계약대로 동작함을 검증한 것이며, 실제 예매처·운영 트래픽 성능이나 네트워크 전달 보장을 의미하지 않는다.

## 8. 후속 경계

- 결제 성공을 신뢰 가능한 서버 검증 결과로 바꾸고 멱등 예약 확정 API에 연결
- 새로고침 후 내 점유를 복구할 수 있는 소유 좌석 조회 계약
- 서버·브라우저 간 명시적 시간대(offset) 계약
- 고경합 상태 변화가 실제 요구될 때 polling, SSE 또는 WebSocket을 비교 측정

대기열·메시지 브로커·실시간 push는 현재 fixture 문제를 해결하는 데 필요하지 않으므로 도입하지 않는다.
