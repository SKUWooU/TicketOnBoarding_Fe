# Checkout 기반 결제·예약 Frontend 연동

## 1. 문제와 목표

기존 결제 화면은 페이지 진입 즉시 외부 PortOne 스크립트를 내려받아 `window.IMP.request_pay`를 호출했다. 결제 성공 callback을 받으면 서버가 발급한 주문 식별자나 결제 금액 검증 없이 legacy 예약 API를 직접 호출했다. 일반 카드와 카카오페이 화면에는 같은 흐름이 중복되어 있었고, 일반 카드 요청 금액은 화면 표시 금액과 다른 `100`으로 고정돼 있었다.

이 구조에서는 브라우저가 만든 주문 번호와 금액을 신뢰하게 되고, callback 중복·새로고침·서버 응답 유실 때 같은 예약이 여러 번 처리될 수 있다. 또한 결제가 실제로 승인됐는지 서버가 검증하기 전에 좌석 예약이 확정되는 문제가 있다.

이번 변경의 목표는 Frontend가 다음 원칙을 따르게 만드는 것이다.

1. 결제 화면으로 이동하기 전에 Backend가 Checkout을 생성한다.
2. 주문 번호와 최종 금액은 Checkout 응답만 사용한다.
3. 결제 결과는 legacy 예약 API가 아니라 검증 예약 API에 전달한다.
4. 동일 작업을 재시도할 때 같은 멱등 키를 재사용한다.
5. 결제 상태가 불명확하면 재결제를 차단한다.
6. 실제 PG는 기본 비활성화하고 fixture 테스트만 수행한다.

## 2. 변경 전후 흐름

### 변경 전

`좌석 선택 → 결제 페이지 이동 → 외부 PG 스크립트 자동 로드 → 브라우저가 금액·merchant_uid 생성 → callback 성공 → legacy 예약 API`

결제 페이지 렌더링 자체가 외부 호출을 시작했으며, callback의 성공 여부가 예약 확정의 유일한 근거였다.

### 변경 후

`좌석 hold → Checkout 준비 → 서버 금액·merchantUid 표시 → 결제 어댑터 → 검증 예약 → 예약 완료`

- `POST /main/detail/{concertId}/checkouts`가 `merchantUid`, `amount`, `expiresAt`, `status`를 반환한다.
- Frontend는 이 응답을 세션에 저장하고 공통 `/payment` 화면으로 이동한다.
- 결제 어댑터가 돌려준 `paymentId`는 `POST /main/detail/{concertId}/checkouts/{merchantUid}/verified-reservation`으로 전달한다.
- 예약 완료 화면은 검증 예약 API가 성공한 뒤에만 열린다.

현재 기본 결제 어댑터는 항상 `PaymentProviderUnavailableError`를 발생시킨다. 따라서 실제 브라우저 실행에서는 외부 PG 스크립트와 API가 호출되지 않으며, 검증 예약 성공 경로는 테스트에서 결제 어댑터와 HTTP를 fixture로 대체해 확인한다.

## 3. 책임 분리

| 구성 요소                | 책임                                                                          |
| ------------------------ | ----------------------------------------------------------------------------- |
| `checkoutApi.js`         | Checkout 준비와 검증 예약 HTTP 계약, `Idempotency-Key` 헤더 전달              |
| `idempotencyKey.js`      | 작업 종류가 드러나는 유일 키 생성                                             |
| `checkoutSession.js`     | 새로고침 후에도 Checkout과 두 멱등 키를 복구                                  |
| `paymentProvider.js`     | PG 구현 경계. 기본 구현은 fail-closed                                         |
| `ConcertReservation.jsx` | 좌석·회차 payload로 Checkout을 먼저 준비하고 성공한 hold만 결제 화면까지 유지 |
| `Payment.jsx`            | 서버 금액 표시, 결제 중복 실행 차단, 검증 예약, 불명 상태 재조회              |

PG SDK, Checkout API, 화면 상태를 한 컴포넌트에 섞지 않았다. 향후 실제 PG를 연결하더라도 `paymentProvider` 경계 안에서만 SDK를 사용하고, 서버 검증 계약과 화면 정책은 유지할 수 있다.

## 4. 멱등성과 새로고침

Checkout 준비 키와 예약 확정 키는 서로 다른 작업이므로 별도로 생성한다.

- Checkout 키: 같은 좌석·회차 Checkout 준비를 재시도할 때 재사용한다.
- 예약 키: 같은 결제 결과의 검증 예약 요청을 재시도할 때 재사용한다.

Checkout 준비 중 503이나 네트워크 실패가 발생해도 좌석·회차 payload가 같으면 메모리에 보관한 Checkout 키를 다시 사용한다. Checkout 준비가 성공하면 Checkout 응답과 두 키를 `sessionStorage`에 저장한다. 사용자가 결제 화면을 새로고침해도 새 주문이나 새 예약 키를 만들지 않는다.

결제 어댑터가 성공하면 `paymentId`를 Backend 검증 요청보다 먼저 세션에 저장한다. 이후 검증 요청의 응답이 유실되더라도 재시도는 PG를 다시 호출하지 않고 저장된 `paymentId`와 예약 키로 검증 예약만 반복한다. 반대로 PG 호출 결과 자체가 불명확하고 `paymentId`를 받지 못했다면 Frontend는 `PAYMENT_ATTEMPT_UNKNOWN`으로 재결제를 차단한다.

인증 토큰이나 사용자 개인정보는 세션에 저장하지 않는다. 예약 확정이 성공하면 세션을 제거한다. 저장 데이터의 형식이 깨졌거나 이전 버전이면 안전하게 폐기하고 결제를 시작하지 않는다.

`sessionStorage`는 중복 요청을 완전히 막는 저장소가 아니다. 탭 단위 재시도를 같은 키로 묶는 Frontend 보조 수단이며, 최종 중복 방지는 Backend의 유일 제약과 멱등 처리에 의존한다.

## 5. 상태 전이와 사용자 동작

| Checkout 상태                  | 화면 정책                                              | 결제 버튼 |
| ------------------------------ | ------------------------------------------------------ | --------- |
| `READY`                        | 서버 금액·주문 번호·점유 만료 시각 표시                | 허용      |
| `PAYMENT_VERIFYING`            | 서버 확인 중임을 알리고 결과 확정 전 재결제를 경고     | 차단      |
| `PAYMENT_VERIFICATION_UNKNOWN` | 결과 확인 필요를 안내하고 관리자 확인 전 재결제를 금지 | 차단      |
| `RESERVATION_CONFIRMED`        | 완료 화면으로 전환                                     | 차단      |
| `EXPIRED`                      | 좌석 점유 만료와 재선택 안내                           | 차단      |

검증 예약 API가 409, 410, 422, 503을 반환하면 성공이나 실패를 브라우저가 임의로 추정하지 않는다. 기존 Checkout 키로 준비 API를 다시 호출해 서버 상태를 조회한다. 조회 결과가 불명확하면 재결제를 차단한다. 특히 503은 “결제 실패”와 같지 않으므로 즉시 재시도 가능한 상태로 단정하지 않는다.

결제 버튼은 React 상태와 별개인 `useRef` 실행 잠금도 사용한다. 같은 렌더링 사이클에서 발생하는 빠른 이중 클릭이 결제 어댑터를 두 번 호출하는 것을 막기 위해서다.

## 6. 오류 계약

| 응답 | Checkout 준비                         | 검증 예약 이후                                      |
| ---- | ------------------------------------- | --------------------------------------------------- |
| 401  | 로그인 화면으로 이동                  | 로그인 화면으로 이동                                |
| 409  | 좌석 상태 변경 안내 후 최신 좌석 조회 | 기존 Checkout 상태 재조회                           |
| 410  | 점유 만료 안내 후 최신 좌석 조회      | `EXPIRED`로 고정하고 재결제 차단                    |
| 422  | 같은 키와 다른 payload 오류 안내      | 기존 Checkout 상태 재조회                           |
| 503  | 같은 키로 재시도 가능함을 안내        | 결제 결과를 추정하지 않고 기존 Checkout 상태 재조회 |

## 7. Fixture 검증

2026-09-03 로컬 Vitest 결과는 11개 파일, 53개 테스트 통과다.

- Checkout 준비·검증 예약 endpoint, body, cookie, 멱등 헤더
- 서버 응답 금액과 주문 번호 사용
- 결제 버튼 이중 클릭에도 결제 어댑터와 검증 예약이 한 번만 실행됨
- Backend 검증 응답 유실 후 동일 `paymentId`로 검증만 재시도하고 PG를 다시 호출하지 않음
- PG 결과 자체가 불명확하면 새 결제를 차단함
- PG 단계의 503을 Backend 검증 503으로 오인하지 않고 재결제를 차단함
- 새로고침 후 Checkout 및 동일 멱등 키 복구
- Checkout 준비의 409·410·422·503이 결제 화면으로 진행되지 않음
- 503 준비 재시도에서 동일 Checkout 키 사용
- 검증 예약 503 이후 `PAYMENT_VERIFICATION_UNKNOWN` 재조회와 재결제 차단
- 기본 어댑터가 `window.IMP`를 호출하거나 PortOne/아임포트 스크립트를 추가하지 않음

빌드는 통과했다. 변경 파일 lint는 오류·경고 0건이며, 저장소 전체 lint는 기존 부채 95 errors·2 warnings가 남아 별도 Issue 범위다. 번들 크기 500 kB 초과 경고도 기존 기준선으로 남는다.

## 8. 검증 범위와 한계

이 결과는 mock HTTP와 가상 결제 어댑터로 Frontend 상태 전이와 계약을 검증한 것이다. 실제 PG 승인 성능, 운영 결제 성공률, 실제 금융 거래, 운영 좌석 재고 성능을 의미하지 않는다.

Backend 기본 결제 검증 어댑터도 실 PG가 설정되지 않으면 503을 반환하므로 현재 로컬 환경에서 실제 FE→PG→BE 성공 E2E를 수행할 수 없다. 다음 통합 단계에서는 외부 네트워크를 사용하지 않는 loopback 전용 fake payment adapter를 별도 Issue로 검토할 수 있다. 이때도 운영 profile에서 활성화되지 않도록 조건을 명시해야 한다.
